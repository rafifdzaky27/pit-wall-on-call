# M1.5 usability test: protocol

- **Goal:** find where first-time players get lost in PitOS before M1.6 and M2 build on it.
- **When:** after the M1.5 build is live. This is the milestone exit gate (desktop spec §10).
- **Who:** 5 people, covering the three proto-personas (desktop spec §3):

| # | Persona | Recruit from |
|---|---|---|
| 1–2 | Dina: junior DevOps or SRE, recently on call | work contacts, DevOps communities |
| 3–4 | Arif: student or bootcamp grad preparing for SRE interviews | campus or bootcamp groups |
| 5 | Maya: senior SRE or team lead | work contacts |

## Session (about 25 minutes, remote or in person, screen shared)

1. **Consent (1 min):** "We are testing the game, not you. I'll record the screen and your voice; the recording stays with me and is deleted after the notes are written. You can stop at any time."
2. **Context (1 min):** "You're on call for an online store. Think aloud: say what you're looking at, what you expect, and what surprises you." Give no other instructions.
3. **Task (up to 12 min):** open the game URL and "play one incident until it ends." Do not help. If they are stuck for 2 minutes, ask "What are you looking for?" and note it as a stuck point.
4. **Probe (5 min):**
   - "What caused the incident?"
   - "What were the first 30 seconds like?"
   - "Was anything on the desktop confusing or pointless?"
   - "What would make you play again tomorrow?"
5. **SUS (3 min):** the 10 standard System Usability Scale statements, answered from 1 (strongly disagree) to 5 (strongly agree):
   1. I think that I would like to use this system frequently.
   2. I found the system unnecessarily complex.
   3. I thought the system was easy to use.
   4. I think that I would need the support of a technical person to be able to use this system.
   5. I found the various functions in this system were well integrated.
   6. I thought there was too much inconsistency in this system.
   7. I would imagine that most people would learn to use this system very quickly.
   8. I found the system very cumbersome to use.
   9. I felt very confident using the system.
   10. I needed to learn a lot of things before I could get going with this system.

   Score: for odd items subtract 1, for even items subtract the answer from 5. Sum the results and multiply by 2.5 (0–100). 68 is average.

## What to record per participant

| Measure | How |
|---|---|
| Time from page to ack | The debrief's "Acknowledged" tile |
| Outcome | Resolved or DNF, budget burned, root cause found |
| Clues found | The debrief's "Clues found" tile |
| Stuck points | Timestamp plus what they were looking for |
| Misreads | Anything they believed that was not true (for example "postgres is the cause") |
| Quotes | Short, verbatim |
| SUS | 0–100 |

## After the sessions

Write the findings to `docs/research/<test date>-m1.5-usability.md`:
- a table of the measures above, one row per participant
- every stuck point, grouped by where it happened (desktop, Browser, Chat, phone, Monitoring, postmortem)
- a severity for each finding: **blocker** (could not continue), **major** (lost more than 1 minute or misread the incident), **minor** (hesitation)
- recommended changes, each tagged to M1.6, M2 or later

Then revise the personas in the desktop spec if the sessions contradict them.
