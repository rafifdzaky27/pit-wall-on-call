# Pit Wall On-Call: incident scenario catalogue for M4

Research notes and 32 scenario candidates. Sources are public postmortems (mostly via the danluu/post-mortems list, https://github.com/danluu/post-mortems), the Google SRE book, and vendor incident reports. The VOID report (https://www.thevoid.community/) and Kubernetes failure stories (https://k8s.af/) were used as pattern sources; the main pattern they confirm is that most incidents are triggered by a change (deploy, config, migration, cert or capacity limit), are prolonged by misleading signals, and are often worsened by the first "obvious" mitigation.

## What the literature says causes incidents

1. Change is the top trigger. Bad deploys, config pushes and migrations recur across Cloudflare, Google, Facebook, Fastly, Allegro and Knight Capital. Config is treated with less rigor than code, and rolls out faster.
2. Limits nobody was watching. Connection pools, disk, file descriptors, integer ranges (Basecamp), transaction id wraparound (Sentry), certificate lifetimes (Azure, Mozilla, Let's Encrypt), quotas.
3. Retry and overload feedback loops. Cascading failure, retry storms and thundering herds turn a small dependency blip into a full outage (Google SRE book chapters "Addressing Cascading Failures" and "Handling Overload").
4. Dependencies and shared control planes. Third parties, DNS, auth, the provider's own status page. AWS DynamoDB DNS race (Oct 2025), Cloudflare and Datadog network incidents.
5. Time. Leap seconds (Google, Linux), clock drift, expiry, timezone and daylight saving bugs.
6. Humans and tooling. Typos in commands (AWS S3 2017), deleting the wrong database (GitLab 2017), cleanup jobs that delete the wrong thing (TravisCI), runbooks that assume state that is gone.
7. Observability failures. Monitoring that shares fate with production, alerts that fire on the symptom of a different problem, dashboards that lag.
8. Rescue actions that hurt. Restarts that drop caches and cause a stampede, failovers that lose writes, scale-ups that hit the database harder.

## Shared service catalogue (proposed for reuse)

edge (gateway/LB), storefront (web), api, checkout, search, auth, worker, queue, cache (Redis), db-primary, db-replica, object-store, cdn, dns, cert store, payments provider, email provider, tax/shipping provider, feature-flag service, cron/scheduler, metrics pipeline. Deploys tool needs per-service history with hidden "flag" and "config" change entries besides code deploys. Almost every scenario below composes from these ten or so shapes:

- A change entry in Deploys (deploy, config, flag, migration, cron edit).
- A resource that saturates (pool, disk, memory, fds, CPU, quota).
- A dependency that degrades (provider, DNS, replica lag).
- A timer (cert, token, key, clock).
- A traffic shape (bot, retry storm, viral spike, thundering herd).

Difficulty scale: 1 = one honest signal and a clear fix; 3 = two plausible causes, needs two tools; 5 = signals mislead, root cause is in an unexpected service, correct fix is not the obvious one and a masking action is very tempting.

## Family A: deploys and config

### A1. The Slow Leak (existing)
- Family: deploys. Grounding: connection leaks after a release are a staple of k8s.af and the VOID report; see also Slack "This was not normal, really" (https://web.archive.org/web/20181208123409/https://slackhq.com/this-was-not-normal-really).
- Customers: intermittent 502, checkout hangs.
- Root cause and fix: deploy leaks DB connections; roll back.
- Red herrings: DB CPU, recent traffic bump. Masking: restart pods, fail over DB.
- Tools: Monitoring, Deploys, DB console, Logs.
- Difficulty 2. Baseline.
- Per-seed: which service shipped it (api, checkout, search), leak rate (time to exhaustion), whether the deploy is the newest or third-newest.

### A2. The Regex That Ate the CPU
- Family: deploys/config. Grounding: Cloudflare 2 July 2019 WAF regex backtracking (https://web.archive.org/web/20211006055154/https://blog.cloudflare.com/details-of-the-cloudflare-outage-on-july-2-2019/).
- Customers: everything on the storefront is slow, then 502/504.
- Root cause and fix: a validation or WAF rule with catastrophic backtracking pushed at the edge; roll back the rule (a config entry, not a code deploy).
- Red herrings: traffic spike, a scheduled report job. Masking: scale out edge (buys minutes, load follows).
- Tools: Monitoring (CPU pinned at edge), Deploys (config history), Logs, Chat.
- Difficulty 3: the culprit is a rule change, not a deploy, and CPU is on the edge not the api.
- Per-seed: which rule (search input, coupon code, address field), which layer.

### A3. Friday Config Push
- Grounding: Google Cloud 2016 autogenerated config incident (https://status.cloud.google.com/incident/compute/16007); Facebook Oct 2021 (https://engineering.fb.com/2021/10/05/networking-traffic/outage-details/).
- Customers: one region or one route returns 404/503.
- Cause and fix: a config push to the routing table removed a route or mis-set a timeout to 0; revert config.
- Red herrings: the deploy that landed an hour earlier; a noisy but unrelated alert. Masking: restart gateway (config reloads from the same bad source).
- Tools: Deploys (config tab), Logs, Browser.
- Difficulty 3. Per-seed: which route, which field (timeout, upstream host, path prefix), typo vs missing key.

### A4. Flag Flip Friday
- Grounding: Knight Capital, 2012, partial deploy plus old flag reused (https://dougseven.com/2014/04/17/knightmare-a-devops-cautionary-tale/).
- Customers: some users get the wrong prices or duplicate orders; others fine.
- Cause and fix: a feature flag enabled for 100% before its dependent service was deployed everywhere; turn the flag off.
- Red herrings: the payment provider showing a few declines; cache. Masking: refunding and pausing orders while leaving the flag on.
- Tools: Deploys (flag history), Chat (a teammate says "we did not touch anything"), Logs, Browser.
- Difficulty 4: state is inconsistent across replicas, so symptoms vary by request. Per-seed: which flag, which % rollout, which node subset is stale.

### A5. The Migration That Locked the Table
- Grounding: CircleCI Nov 2021 database change (https://discuss.circleci.com/t/incident-report-november-8-2021-jobs-stuck-in-a-not-running-state/41890); common Postgres ALTER TABLE lock stories.
- Customers: checkout spins, orders stuck.
- Cause and fix: a schema migration holds an exclusive lock and every query queues behind it; kill or cancel the migration, then rerun it safely.
- Red herrings: connection count rising (a symptom), api latency. Masking: raise pool size, restart api.
- Tools: DB console (blocked queries, lock waits), Deploys (migration entry), Logs.
- Difficulty 4: the "pool exhausted" signal looks like A1 on purpose. Per-seed: table (orders, carts, users), migration type.

### A6. Half-Rolled Canary
- Grounding: k8s.af rollout stories; Google SRE "Canarying releases".
- Customers: about 1 in 4 requests error; refresh sometimes fixes it.
- Cause and fix: one version in the pool is bad while the rest are fine; halt rollout and roll back the canary.
- Red herrings: the load balancer, flaky network. Masking: retries in the client, restarting healthy pods.
- Tools: Monitoring (per-version error rate), Deploys, Browser (refresh twice).
- Difficulty 2 to 3. Per-seed: the error fraction, the bad version, whether monitoring is aggregated (hides it) or per instance.

### A7. Secret Rotated, Nobody Told the Worker
- Grounding: Heroku config variable incident (https://blog.heroku.com/how-i-broke-git-push-heroku-main); Facebook internal credential and tooling fallout.
- Customers: order emails and receipts stop; storefront looks healthy.
- Cause and fix: an API key was rotated but one worker still has the old one; update the secret and restart that worker.
- Red herrings: email provider status shows minor degradation; queue depth. Masking: retry all failed jobs (they fail again).
- Tools: Logs (401 lines), Incident (provider status), Queue view, Chat.
- Difficulty 3. Per-seed: which secret, which provider, which consumer.

## Family B: capacity and resource exhaustion

### B1. Disk Full at 3AM
- Grounding: GitLab 2017 and countless log-volume stories; Sentry, Travis storage stories.
- Customers: checkout errors on writes, browsing OK.
- Cause and fix: log or WAL volume fills the DB or worker disk; clean or rotate, then fix the retention setting.
- Red herrings: sudden write latency, replica lag. Masking: fail over to the replica (same disk pattern, and data loss risk).
- Tools: Monitoring (disk graph), DB console, Logs.
- Difficulty 2. Per-seed: which volume (db WAL, worker tmp, log agent), rate of fill, whether a debug flag was left on.

### B2. Out of File Descriptors
- Grounding: Slack and k8s.af "too many open files" patterns.
- Customers: random connection resets, some images missing.
- Cause and fix: a service leaks sockets and hits ulimit; roll back the leak or raise limit plus fix.
- Red herrings: network, the CDN. Masking: restart (cyclic recurrence every N minutes).
- Tools: Logs ("EMFILE"), Monitoring, Deploys. Difficulty 3. Per-seed: which service, recurrence period.

### B3. OOM Kill Loop
- Grounding: k8s.af memory limit stories.
- Customers: pages intermittently 503, latency saw-tooth.
- Cause and fix: a deploy raised memory per request or a limit was cut; pods OOMKilled and restart; raise limit or revert.
- Red herrings: "unhealthy nodes", the DB. Masking: add replicas (each still ooms).
- Tools: Monitoring (restarts), Logs, Deploys. Difficulty 2 to 3. Per-seed: service, limit vs leak.

### B4. The Viral Spike
- Grounding: Reddit and flash-sale stories; Google SRE "Handling Overload" (https://sre.google/sre-book/handling-overload/).
- Customers: slow storefront, checkout timeouts, but no errors in logs.
- Cause and fix: legitimate traffic (influencer post, flash sale) exceeds capacity; scale out, shed load and enable a waiting-room/rate-limit on non-critical routes.
- Red herrings: "DDoS", the latest deploy. Masking: blocking the top IPs (real users).
- Tools: Monitoring, Chat (marketing says "the promo just went out"), Logs, Incident (status page).
- Difficulty 2. Per-seed: source (email blast, social, partner), route hit.

### B5. Autoscaler Stuck at Two
- Grounding: k8s.af HPA stories; AWS quota stories.
- Customers: slow at peak hours, fine off-peak.
- Cause and fix: autoscaler hit a quota or max-replica setting; raise cap.
- Red herrings: slow query, a noisy neighbor. Masking: restarting pods.
- Tools: Monitoring, Deploys (config), Logs. Difficulty 3. Per-seed: which limit (quota, max, cpu request misconfigured).

### B6. The Batch Job at Noon
- Grounding: common cron-overlap stories; TravisCI cleanup (https://web.archive.org/web/20221220114914/https://blog.travis-ci.com/2016-09-30-the-day-we-deleted-our-vm-images/).
- Customers: slowness every hour on the hour.
- Cause and fix: a new cron report competes with production for the primary; move to a replica or pause it.
- Red herrings: traffic, cache expiry. Masking: scale the api.
- Tools: Monitoring (periodic pattern), DB console (long-running query), Deploys (cron history). Difficulty 3. Per-seed: period, job name.

## Family C: dependencies and third parties

### C1. The Payment Provider Blinks
- Grounding: many Stripe/Adyen partial outages; Google SRE "Addressing Cascading Failures" (https://sre.google/sre-book/addressing-cascading-failures/).
- Customers: "payment failed" at checkout; rest of site fine.
- Cause and fix: provider latency spikes; checkout threads block. Enable the fallback (secondary provider or queued authorization), post to the status page.
- Red herrings: your own recent deploy, DB. Masking: restart checkout (threads block again).
- Tools: Logs (provider timeouts), Incident (provider status, status page), Browser. Difficulty 2. Per-seed: which provider, whether the fallback is configured, whether the provider status page is honest.

### C2. Retry Storm
- Grounding: Google SRE cascading failures; Spotify backoff story; AWS DynamoDB Oct 2025 (https://aws.amazon.com/message/101925/) for the recovery retry pileup.
- Customers: timeouts everywhere, even after the original blip ended.
- Cause and fix: a short dependency error caused clients to retry aggressively; the load keeps the dependency down. Disable or back off retries, shed load, let it recover.
- Red herrings: the dependency is now "healthy" in its own dashboard. Masking: restart the dependency (the storm returns).
- Tools: Monitoring (request amplification), Logs, Chat. Difficulty 4. Per-seed: which edge amplifies, retry count.

### C3. Shipping Rates Timeout
- Grounding: third-party latency pattern in Google SRE.
- Customers: cart page hangs, "Calculating shipping...".
- Cause and fix: shipping/tax API slow; add timeout and cached rates via config, degrade gracefully.
- Red herrings: search service (loaded on same page), the DB. Masking: scale api.
- Tools: Browser (network waterfall), Logs, Chat. Difficulty 2. Per-seed: which provider.

### C4. The Expired Cert
- Grounding: Azure Feb 29 2012 (https://azure.microsoft.com/en-us/blog/summary-of-windows-azure-service-disruption-on-feb-29th-2012/); Mozilla add-ons 2019 (https://web.archive.org/web/20250303152906/https://hacks.mozilla.org/2019/07/add-ons-outage-post-mortem-result/); Let's Encrypt root expiry (https://letsencrypt.org/docs/dst-root-ca-x3-expiration-september-2021/).
- Customers: browser cert warning on one host, or mobile app fails while web works.
- Cause and fix: an internal or partner-facing cert expired; renew and deploy, add expiry alert.
- Red herrings: "the gateway is down" (it is up), a recent deploy. Masking: restarting the gateway; disabling TLS verification.
- Tools: Browser (cert error), Logs (x509), Monitoring. Difficulty 2 to 3. Per-seed: which cert (public, mTLS to payments, DB TLS), which host.

### C5. The Auth Service Sneezes
- Grounding: shared control plane pattern (Google auth outage Dec 2020; Cloudflare Nov 2025, https://blog.cloudflare.com/18-november-2025-outage/, for a generated file breaking a core proxy).
- Customers: random logouts and 401s; cart empty after refresh.
- Cause and fix: auth dependency rate-limits or a token signing key rotated; restore the key or raise the limit.
- Red herrings: session cache, cookie change. Masking: clearing sessions (forces everyone to re-login and makes load worse).
- Tools: Logs, Deploys, Chat. Difficulty 4. Per-seed: key vs limit vs clock.

### C6. The CDN Purge Party
- Grounding: Fastly 8 June 2021 (https://www.fastly.com/blog/summary-of-june-8-outage); many CDN misconfig stories.
- Customers: old or broken assets, unstyled page, or stale prices.
- Cause and fix: CDN config change or purge-all sends all traffic to origin, or serves the wrong version; revert CDN config, warm the cache.
- Red herrings: origin CPU (a symptom), storefront deploy. Masking: scale origin.
- Tools: Browser (view assets), Monitoring, Deploys (CDN config). Difficulty 3. Per-seed: purge vs bad cache key vs bad TTL.

## Family D: data and databases

### D1. Replica Lag Shows Old Carts
- Grounding: GitHub Oct 2018 replication (https://github.blog/news-insights/the-library/downtime-last-saturday/).
- Customers: item disappears from cart, order history stale, double-click purchases.
- Cause and fix: replica lag after heavy writes; route reads-after-writes to primary temporarily and find the long transaction.
- Red herrings: cache; the api deploy. Masking: flushing the cache; failing over to the lagging replica (loses writes).
- Tools: Monitoring (lag), DB console, Browser. Difficulty 4. Per-seed: which reads, cause (batch, long txn, network).

### D2. The Integer Ran Out
- Grounding: Basecamp Nov 2018 (https://web.archive.org/web/20220529044310/https://m.signalvnoise.com/postmortem-on-the-read-only-outage-of-basecamp-on-november-9th-2018/).
- Customers: cannot place new orders; browsing fine.
- Cause and fix: primary-key column (int) hit 2^31; migrate to bigint (temporary sequence bump as stop-gap).
- Red herrings: DB is "healthy", recent deploy. Masking: restart api.
- Tools: Logs ("out of range"), DB console. Difficulty 3. Per-seed: which table.

### D3. Vacuum Never Finished
- Grounding: Sentry Postgres transaction id wraparound (https://blog.sentry.io/2015/07/23/transaction-id-wraparound-in-postgres).
- Customers: DB becomes read-only, writes fail.
- Cause and fix: long-running transaction or disabled autovacuum blocked freezing; kill txn, run vacuum.
- Red herrings: disk, CPU. Masking: failover (new primary has same problem).
- Tools: DB console, Logs, Monitoring. Difficulty 5. Per-seed: cause of blocked vacuum.

### D4. The Missing Index
- Grounding: many; Allegro (https://allegro.tech/2018/08/postmortem-why-allegro-went-down.html) for similar surprise DB load.
- Customers: search slow, then whole site slow.
- Cause and fix: a new query pattern (or dropped index) causes seq scans; add index or revert the deploy.
- Red herrings: traffic, cache hit rate. Masking: bigger DB instance.
- Tools: DB console (slow queries), Deploys. Difficulty 3. Per-seed: table, query, or index dropped by migration.

### D5. Oops, Wrong Database
- Grounding: GitLab 2017 (https://docs.google.com/document/d/1ScqXAdb6BjhsDzCo3qdPYbt1uULzgZqPO8zHeHHarS0/preview); AWS S3 2017 (https://aws.amazon.com/message/41926/).
- Customers: missing recent orders or products; some pages 404.
- Cause and fix: a cleanup command ran against production; stop it, restore from backup, communicate honestly. Time-pressure scenario with fewer clean answers.
- Red herrings: cache invalidation, recent deploy. Masking: rebuild cache from the now-wrong data.
- Tools: DB console, Chat (a teammate admits it late), Incident. Difficulty 5. Per-seed: table, teammate involved, age of last good backup.

## Family E: networking, DNS, TLS

### E1. DNS Says Nope
- Grounding: GitHub DNS outage (https://github.blog/news-insights/the-library/dns-outage-post-mortem/); AWS DynamoDB DNS race (https://aws.amazon.com/message/101925/).
- Customers: intermittent errors that vary by user; other regions fine.
- Cause and fix: DNS record removed or wrong TTL, an internal resolver empty; restore the record.
- Red herrings: the service (which is healthy), the LB. Masking: restart the services; add hosts-file hacks.
- Tools: Logs ("no such host"), Browser, Chat. Difficulty 4. Per-seed: which record (api-internal, db, payments).

### E2. Firewall Rule Over-Enthusiasm
- Grounding: Stack Overflow Aug 2014 (https://web.archive.org/web/20201020103424/https://stackstatus.net/post/96025967369/outage-post-mortem-august-25th-2014).
- Customers: one region or office cannot connect; the rest fine.
- Cause and fix: a firewall or security-group change blocked a subnet; revert rule.
- Red herrings: ISP, the deploy. Masking: bypass WAF entirely.
- Tools: Deploys (infra changes), Logs (timeouts), Browser. Difficulty 3. Per-seed: which subnet or port.

### E3. Slow Network, Not Slow App
- Grounding: Cloudflare byzantine failure (https://web.archive.org/web/20211015231917/https://blog.cloudflare.com/a-byzantine-failure-in-the-real-world/); Datadog Cilium (https://www.datadoghq.com/blog/2023-03-08-multiregion-infrastructure-connectivity-issue/).
- Customers: random timeouts at 5s.
- Cause and fix: packet loss between two zones after a node/CNI change; drain the bad node or zone.
- Red herrings: DB, GC pauses. Masking: restart pods (reschedule to bad nodes).
- Tools: Monitoring (per-node), Logs, Chat. Difficulty 5. Per-seed: which node/zone.

## Family F: caching

### F1. Cache Stampede After Restart
- Grounding: Discord Redis failover (https://status.discordapp.com/incidents/qk9cdgnqnhcn); Facebook's classic thundering herd stories.
- Customers: a spike of slowness right after "fix"; product pages slow.
- Cause and fix: cache wiped (restart or eviction) and everything hits the DB; enable request coalescing, warm keys, throttle traffic.
- Red herrings: DB slow queries. Masking: scale api (more requests to DB).
- Tools: Monitoring (hit rate), Logs, DB console. Difficulty 3. Per-seed: trigger (oom, failover, mistaken flush).

### F2. Poisoned Cache
- Grounding: Cloudflare and CDN cache key incidents; Fastly.
- Customers: some users see someone else's data or wrong currency.
- Cause and fix: cache key missing a vary dimension after deploy; fix key, purge, communicate.
- Red herrings: session bug, auth. Masking: shortening TTL.
- Tools: Browser (switch account), Logs, Deploys. Difficulty 4 (also a security angle). Per-seed: which dimension (locale, currency, user).

## Family G: queues and async

### G1. Poison Pill
- Grounding: Kafka/SQS stuck-consumer stories in the VOID.
- Customers: order confirmations and inventory updates late.
- Cause and fix: one malformed message blocks a consumer (retries forever); move to dead-letter, ship a validator.
- Red herrings: queue depth alone, provider status. Masking: purge the queue (loses valid orders).
- Tools: Logs, Queue view, Chat. Difficulty 3. Per-seed: which queue, message type.

### G2. Consumer Fell Behind
- Grounding: Slack incidents on job queues.
- Customers: "your order is processing" for hours.
- Cause and fix: consumer scaled to zero or crashed silently after a config edit; restore replicas.
- Red herrings: the payment provider; DB. Masking: replaying the queue from the start (duplicate charges).
- Tools: Monitoring, Deploys, Queue. Difficulty 2. Per-seed: queue, cause.

## Family H: time and clocks

### H1. Leap Second, Loud
- Grounding: Google leap second (https://status.cloud.google.com/incident/compute/15056#5719570367119360); Linux 2009 (https://web.archive.org/web/20220427012208/https://lkml.org/lkml/2009/1/2/373).
- Customers: random hangs at a specific time, then recovery.
- Cause and fix: time jump or smear mismatch; fix NTP config on the affected nodes.
- Red herrings: GC, load. Masking: restart (the same after resync).
- Tools: Logs (timestamps out of order), Monitoring, Chat. Difficulty 5. Per-seed: node group, direction of drift.

### H2. Token Expires at Midnight UTC
- Grounding: Azure leap-day cert bug (linked above); JWT lifetime bugs.
- Customers: users logged out at exact hour boundary; API clients see 401.
- Cause and fix: token TTL or key validity computed in local time after a config change; fix TTL/timezone.
- Red herrings: auth deploy. Masking: extending sessions manually.
- Tools: Logs, Deploys, Chat. Difficulty 3. Per-seed: timezone vs TTL.

- Grounding: common; Cloudflare/Fastly bot reports. Google SRE "Handling Overload".

- Cause and fix: botnet hitting /login; rate-limit and challenge on that route, not block globally.
- Red herrings: auth service bug; DB. Masking: scaling auth (pays for the attack).
- Tools: Logs (IPs, user agents), Monitoring, Incident. Difficulty 3. Per-seed: route (login, search, coupon), pattern.

### I2. Scraper Melts Search
- Grounding: seen in Reddit, Twitter, and marketplace incidents.
- Customers: search results slow, filters time out.
- Cause and fix: one crawler with unbounded queries; rate-limit and cache.
- Red herrings: search index rebuild; recent deploy. Masking: restarting search cluster.
- Tools: Logs, Monitoring. Difficulty 2. Per-seed: crawler UA, endpoint.

## Family J: human and operational error

### J1. Cleanup Job Cleans Too Much
- Grounding: TravisCI VM image deletion (https://web.archive.org/web/20221220114914/https://blog.travis-ci.com/2016-09-30-the-day-we-deleted-our-vm-images/).
- Customers: product images missing (broken), some downloads 404.
- Cause and fix: a lifecycle rule deleted live objects; disable rule, restore from versioning.
- Red herrings: CDN, storefront deploy. Masking: purge CDN (destroys the cached copies that were the only survivors).

### J2. Wrong Environment
- Grounding: Heroku, S3 typo pattern; GitLab.
- Customers: staging emails to real users, or test payments; some orders wrong.
- Cause and fix: staging config pointed at production dependencies; stop, point back, communicate.
- Red herrings: email provider. Masking: disabling the email provider entirely (breaks real emails).
- Tools: Logs, Deploys, Incident. Difficulty 3.

### J3. On-Call Runbook Is Wrong
- Grounding: GitLab 2017; Roblox Consul (https://blog.roblox.com/2022/01/roblox-return-to-service-10-28-10-31-2021/) for lack of internal tools during outage.
- Customers: prolonged partial outage.
- Cause and fix: a teammate's runbook says "restart the queue", which loses data; correct fix is elsewhere. Tests trust and verification of Chat.
- Red herrings: the runbook's step. Masking: following the runbook.
- Tools: Chat (contradictory answers), Logs, Deploys. Difficulty 4. Per-seed: which teammate is wrong.

## Family K: observability failures

### K1. The Dashboard Lies
- Grounding: Facebook 2021 (monitoring and tools shared fate), Roblox.
- Customers: users complain, dashboards green.
- Cause and fix: metrics pipeline delayed or an exporter broken; use Browser and Logs directly to find the real failure.
- Red herrings: "customers are wrong", browser cache. Masking: silence alerts.
- Tools: Browser, Logs, Chat. Difficulty 4. Per-seed: which panel is stale, delay length.

- Grounding: PagerDuty/incident.io on alert fatigue; Datadog network incident.
- Customers: checkout slow, everything else fine.
- Cause and fix: 20 alerts fire, all derivative of a single root cause (DB primary IO); find root, ignore noise.
- Red herrings: the loudest alert. Masking: acking alerts and paging more people.
- Tools: Monitoring, DB console, Incident. Difficulty 3. Per-seed: root among 4 candidates.

## Design principles for a daily that is hard but fair

1. Every signal is honest but incomplete. Never fabricate a false metric; instead pick which true signals are visible first (lag, aggregation, per-instance vs global). Misleading comes from omission and timing, not lies. Exception: teammates in Chat may be wrong, but they should say something checkable.
2. Two or three plausible causes each day. Each scenario ships with a "recent deploy" that is innocent, a noisy metric that is a symptom, and one true cause. The player should be able to falsify the innocent ones with a tool.
3. Every scenario has a masking action that gives relief for N minutes then recurs (restart, failover, scale-out), plus one harmful action (purge, replay, wipe). Use consistent scoring: masking adds time, harmful adds damage.
4. Time pressure through a visible burn: revenue per minute, customer complaint count, an SLA timer. Escalate: after a few minutes the incident worsens (spike or second alert) unless the player acts.
5. Fair means discoverable. For each scenario there is always at least one tool path that reaches the root cause in under about 6 actions. Hints are available (Chat) but cost time.
6. Per-seed variation on four axes: which service is affected, which trigger (deploy, config, flag, cron), the magnitude and timing, and which distractor. Same cause chain, different nouns and numbers. Keep the fix action category constant but the target parameter different (which cert, which rule) so memory helps with pattern, not answer.
7. Chain scenarios: a real incident often has a secondary problem exposed by the fix (retry storm after the dependency recovers, stampede after restarting). Use in hard tier.
8. Debrief: after resolving, show the true timeline and what the player's masking actions did. This is how the game teaches.
9. Rotate families: avoid the same family on consecutive days; weight difficulty on a weekly curve (easy Monday to hard Friday).

## Recommended first batch of 8 for M4

Spread: 6 families, difficulty 2 to 5. Reuses shared services (db, cache, queue, gateway, payments provider) and the Deploys/Logs/DB console tools already built.

1. B1 Disk Full at 3AM (difficulty 2). Simplest new mechanic (resource fills over time) and near-zero new tooling; a good second scenario after A1.
