# M6 Hard Mode Implementation Plan

**Spec:** `docs/specs/2026-10-01-m6-hard-mode-design.md` (read it first; H1–H13 are binding).

**Execution:** a foundation commit on `feat/m6-hard-mode` (done), then four parallel workstreams on Sonnet in their own worktrees, then Claude integrates, removes the content harness's skip, runs a fresh review, and ships.

## Foundation (already on the branch)

- `ActionDef.cli?: string` in `packages/engine/src/types.ts` (content only; engine never reads it).
- `packages/scenarios/src/kit/cli.ts`: `normaliseCli`, `cliFirstWord`, `cliIsBalanced`; `CLI_VOCABULARY` in `registry.ts`; all exported from `@pitwall/scenarios`.
- `packages/scenarios/src/cli.content.test.ts`: the content harness. It skips an incident whose actions have no `cli` yet; integration removes the skip.
- `Prefs.difficulty: "normal" | "hard"` (default normal) in `apps/web/src/os/prefs.ts`.
- `useIncident().difficulty`: the pref until the shift leaves idle, then fixed; training is always normal (`apps/web/src/os/incident/IncidentProvider.tsx`, test `difficulty.test.tsx`).

## Global constraints

- TDD: failing test first, watched failing.
- No emoji or decorative icons; DESIGN.md tokens; status as text. `localStorage` only in try/catch.
- Do not change `ENGINE_VERSION`, golden files, or scoring.
- Commits: plain messages, no attribution lines, never `--no-verify`.
- Gate before handing back: `pnpm lint`, `pnpm typecheck`, `pnpm test`; web workstreams also `pnpm e2e`.

## Command conventions (A1 and A2 must both follow these)

Use the same family for the same kind of action everywhere. `<svc>` is the action's service id as it appears on the map (`checkout`, `payments`, …).

| Kind | `cli` |
|---|---|
| Read a service's recent logs | `kubectl logs deployment/<svc> --since=15m` |
| Search logs for something | `kubectl logs deployment/<svc> --since=1h \| grep -i <word>` |
| Inspect a deployment (image, env, events) | `kubectl describe deployment/<svc>` |
| Pod resource use | `kubectl top pods -l app=<svc>` |
| Deploy history | `kubectl rollout history deployment/<svc>` |
| Roll back the last deploy | `kubectl rollout undo deployment/<svc>` |
| Restart | `kubectl rollout restart deployment/<svc>` |
| Scale | `kubectl scale deployment/<svc> --replicas=<n>` |
| Change an env/config value | `kubectl set env deployment/<svc> <KEY>=<value>` |
| Feature flag | `flagctl disable <flag>` / `flagctl enable <flag>` |
| A metric query (dashboard checks) | `promtool query instant http://prometheus:9090 '<promql>'` |
| SQL (DB console; reuse the action's `command` verbatim) | `psql -c "<SQL>"` |
| Redis | `redis-cli <args>` |
| HTTP probe of a dependency | `curl -s <url>` or `curl -sI <url>` |
| TLS certificate check | `openssl s_client -connect <host>:443 -servername <host>` |
| Disk on a host | `df -h <path>` / `du -sh <path>/*` |
| Delete files | `rm -rf <path>` (reuse `command` if present) |
| Queue/consumer inspection | `kafka-consumer-groups --bootstrap-server kafka:9092 --describe --group <group>` |
| Incident process (status page, escalate, comms) | `incidentctl <verb> ...` (e.g. `incidentctl status-page "Investigating checkout errors"`, `incidentctl page secondary`) |

If an action fits none of these, pick the most realistic real-world command and say so in your report. Every `cli` must name the concrete target the normal-mode button acts on (the right service, slot, flag), so typing it is a real decision.

## Workstream B: Terminal and hard-mode UI (apps/web)

1. **Parser** `apps/web/src/os/apps/terminal/commands.ts`: `runLine(line, ctx)` → output lines and an optional action id to dispatch. Builtins `help`, `ack`, `status`, `services`, `history`, `clear` (H7). Match per H5 against `scenario.actions` using `normaliseCli`; offered → dispatch; matched but not offered → tool-family "not found" text (per first word: kubectl `Error from server (NotFound): …`, psql `ERROR: … does not exist`, generic otherwise) with no dispatch; busy (`check(id)` returns a busy reason) → "another operation is in progress"; unknown → `<word>: command not found` plus "did you mean" from builtins + `CLI_VOCABULARY` (edit distance ≤ 2), never scenario commands (H6). Unit tests for each branch, including a test that no suggestion or error text ever contains a scenario-only identifier.
2. **Completion** `complete(input, ctx)` (H8): first word from builtins + `CLI_VOCABULARY`; after `deployment/` or `-l app=`, service ids from the map. Unit tests including "never completes a slot/flag name".
3. **Terminal app** `apps/web/src/os/apps/terminal/TerminalApp.tsx`: registered in `os/apps/registry.tsx` and `ids.ts`; in the dock only when `incident.difficulty === "hard"` during a shift; opens automatically on the first ack of a hard shift. Scrollback, prompt `oncall@pitwall:~$`, ↑/↓ history per shift, Tab, Ctrl+L, Ctrl+C. Shows `running… (Ns)` then the action's finding lines when it completes (reuse `outputsOf` from `tools/toolActions.ts`). Accessible: the output is an `aria-live="polite"` log; the input is labelled.
4. **Hide action buttons in hard mode** (H2): ActionsPanel in Monitoring, Logs, Deploys, DB console, Incident app show "Hard mode: run commands in Terminal" instead of their action lists; read-only views stay. Chat `/ask` stays.
5. **Settings → Gameplay → Difficulty** (Normal / Hard) with one line explaining each; mid-shift change shows "Applies from your next shift". Status chip shows "Hard" in a hard shift.
6. Analytics: add `difficulty` to `shift_start` and `shift_finish` props (update the allowlist in `analytics.ts` and its tests).
7. e2e `e2e/hard-mode.spec.ts`: set difficulty hard in Settings, start a shift, ack, solve the pinned e2e incident (`db-pool-exhaustion`, a slow-leak variant; see `VITE_PIN_INCIDENT`) by typing its golden actions' `cli` (read from the scenario at runtime, never hard-coded strings) in Terminal, and reach the resolved results card. Workstream A1 writes those `cli` values in parallel, so guard the spec with `test.skip(<no cli on the golden actions>, "needs M6 content")`; integration removes the guard. To check your spec works, add the `cli` values locally without committing them.

## Workstream C: per-difficulty runs and leaderboards

1. **API** (`apps/api`): `difficulty` in the POST body (zod enum, default `normal`), Drizzle migration adding `runs.difficulty text not null default 'normal'` with check `in ('normal','hard')`; the unique ranked-daily index and both board indexes include `difficulty` (drop and recreate in the same migration is fine because the index changes are additive in behaviour; keep the migration backward compatible with the previous image: old image writes no difficulty → default normal). `GET /api/leaderboard` and the daily board take `difficulty` (default normal); the POST answer's board is for the run's difficulty. Integration tests: a hard run and a normal run of the same daily are both ranked; boards do not mix; old clients without the field land on normal.
2. **Web submission** (`apps/web/src/net/*`): send `useIncident().difficulty` with every run, including queued offline submissions (old queued items without it are normal).
3. **Leaderboard UI:** Normal / Hard switch on daily and practice tabs (H11), remembered in localStorage (try/catch); empty state for a hard board with no runs yet.
4. **Results card and share text** say "Hard" for a hard run.
5. Retention SQL in `apps/api/sql/` gains a per-difficulty split where it makes sense (finish rate by incident and difficulty); keep the existing tests passing and add one.
